# The TCK contract

This document is for people who write a TCK engine or add corpus entries. It defines what a corpus entry contains, how its queries are resolved, how types are rendered so that two engines can be compared, and what is checked. For what the queries are *about* (what the SLS says and what scalac does), see [SPEC-GAPS.md](SPEC-GAPS.md).

There are two engines:

- `ScalacEngine` ([`reference/ScalacEngine.scala`](../reference/ScalacEngine.scala)) embeds `scala.tools.nsc.Global`. It is the oracle that generates the goldens.
- The IntelliJ engine (`TypeSystemTckTest` in intellij-scala) answers the same queries through the PSI type system and compares its answers with the goldens.

Both implement `TckEngine` ([`reference/Tck.scala`](../reference/Tck.scala)).

## 1. A corpus entry

An entry is a directory `corpus/NN-name/` with three files.

**`source.scala`: the preamble.** Ordinary Scala 2.13 declarations. It may contain `/*ANCHOR id*/` markers at statement positions (section 3). The preamble together with its spliced queries must be a legal program: it has to compile through `refchecks` (section 5).

**`tck.json`: the queries.** Every field except `description`, `concepts`, `types`, `conformance` and `baseTypeSeq` is optional.

| Field | Shape | Meaning |
|---|---|---|
| `description` | string | One line: the concept and the expected answer |
| `concepts` | list of strings | Tags, e.g. `self-type`, `asSeenFrom` |
| `types` | `[{name, expr, anchor?}]` | Named type expressions. `expr` is Scala type syntax, resolved at the top level of the preamble or at `anchor` |
| `conformance` | `[{lhs, rhs, expect}]` | `lhs <: rhs` over names from `types`; `expect` is human-authored |
| `equivalence` | `[{lhs, rhs, expect}]` | `lhs =:= rhs`; `expect` is human-authored |
| `baseTypeSeq` | list of names from `types` | Record the base type sequence and the linearization (`baseClasses`) of each |
| `termTypes` | `[{name, expr, anchor?}]` | Term probes. `expr` is a Scala expression; the probe records the type inferred for `val p = expr` |
| `baseTypes` | `[{name, prefix, clazz}]` | Record `prefix baseType C`, where `C` is the class of the type named `clazz` |

**`expected.json`: the goldens.** Generated by `scala-cli run reference -- generate`, never edited by hand. It holds scalac's answer for every query: `conformance` and `equivalence` (as `{lhs, rhs, holds}`), and `baseTypeSeq`, `baseClasses`, `termTypes` and `baseTypes` (rendered as in section 4).

## 2. How a query is resolved

The reference engine wraps the preamble in a synthetic `object __tck.Corpus`. It adds `type __q_<name> = <expr>` for each entry in `types` and `val __t_<name> = <expr>` for each entry in `termTypes`. A declaration without an anchor goes at the top level of `Corpus`; one with an anchor is spliced at its marker. The engine compiles to the end of typer and reads the answers off the typed trees: the dealiased alias for a type, and the inferred result type of the `val` for a probe.

Another engine must resolve each expression in the same scope. IntelliJ does this with `createTypeElementFromText`, using the PSI element at the marker as the context.

## 3. Anchors: context-dependent types

Some types exist only relative to a particular `this`, so they cannot be named from the top level:

- the `this.type` of a class or trait;
- a member relative to `this` (`this.T`);
- a self-type witness: with `trait AnimalBox { self: Animal => }`, the instance being an `Animal` is visible only through `AnimalBox.this`.

The preamble marks the place with `/*ANCHOR <id>*/`, and a query names it. The query is resolved *as if written at the marker*, so `this`, the self type and the members in scope resolve as they would there.

```scala
trait AnimalBox { self: Animal =>
  type T
  /*ANCHOR inAnimalBox*/
}
```
```json
{ "name": "AnimalBoxThis", "expr": "this.type", "anchor": "inAnimalBox" }
```

This is where SCL-21947 lives. `AnimalBox <: Animal` is false, but `AnimalBox.this.type <: Animal` is true, and the self type is part of `AnimalBox.this`'s base type sequence (`AnimalBox with Animal` heads it). An engine that resolves `this.type` without the anchor's context gets both wrong.

## 4. Rendering normal form

The two engines print types differently, so goldens use a canonical rendering. Both engines must produce exactly this string. If an engine renders a type differently, it is non-conforming even when its internal type is morally equal. Where these rules are ambiguous, scalac's output (the goldens) decides, and the rule is tightened here.

- **Corpus symbols** are named relative to the corpus module, with `#` for nesting: `Animal`, `Outer#Inner`. The wrapper prefix `__tck.Corpus.` never appears.
- **Library symbols** use their fully qualified name: `scala.Any`, `scala.collection.immutable.List`, `java.lang.String`.
- **Type aliases** are dealiased before rendering, so `String` and `Predef.String` render the same way.
- **Type application:** `Name[Arg1, …, ArgN]`, with the arguments rendered recursively.
- **Refinements:** `Parent1 with Parent2 { decls }`, with the declarations sorted by name. A type member renders as `type X = T` or `type X >: L <: U`, a term member as `def x: T`.
- **Path-dependent types** keep their path: `Impl.this.Tree`, `Use.this.global.Symbol`.
- **Singleton types** render as `p.type`, where `p` is the full path (`Use.this.b.x.type`, not just the member). A class's this-type is `C.this.type`; a refinement's this-type is `this.type`.
- **Existentials** render as `T forSome { type _1 >: L <: U; … }`. Quantifiers are numbered `_1`, `_2`, … in order of appearance, since scalac's own names (`_1.type`, a captured local's name) are implementation details. Bounds are always written out, so `_` becomes `>: scala.Nothing <: scala.Any`.

`baseClasses` entries are class names in the same form.

## 5. What is checked

For every entry, `scala-cli run reference -- verify` and the munit suite (`scala-cli test reference`) check:

- **Legality:** the preamble with its spliced queries compiles through `refchecks`. This is needed because the engine reads types after typer, and typer accepts some programs that scalac rejects. The old corpus 18 was one (SPEC-GAPS.md §3).
- **Conformance and equivalence** against the human-authored `expect`. This validates the harness, and it validates the human's expectations against the oracle.
- **No drift:** every recorded `baseTypeSeq`, `baseClasses`, `termTypes` and `baseTypes` answer equals the committed golden, and every entry has a golden.

CI ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)) runs both. It also regenerates all goldens and fails on any diff, which catches a new query without a golden.

An engine under test is checked the same way, with its answers compared to the goldens. A divergence on base types usually falls into one of these classes:

- **Order:** same members, different order. `baseTypeSeq` order is scalac's symbol-id order, not linearization order (SPEC-GAPS.md §3). Mixin-order bugs show up in `baseClasses`.
- **Membership:** a base type that one engine has and the other doesn't.
- **Merge or rendering:** the same class in both, with different arguments or prefix.
- **Approximation seam:** a difference only where scalac's depth limits approximate (SPEC-GAPS.md §3, §4). It is not a failure unless a conformance query can observe it.

## 6. Adding an entry

1. Create `corpus/NN-name/source.scala` and `tck.json`. Entries are numbered and progressive: each one adds one concept on top of earlier ones, so a failing early entry explains later failures. Start `source.scala` with a comment that says what the entry pins down and why, with references (SPEC-GAPS.md section, scalac code, issue).
2. Write `expect` for conformance and equivalence from your own understanding, not from scalac's output. A mismatch is a finding, either in the harness or in your understanding.
3. Run `scala-cli run reference -- generate`, read the new `expected.json`, and run `verify`.
4. Commit the three files together.
